## 요약문

시간표를 비트 벡터로 변환하여 공통 공강 시간을 계산하고, 이동 여유 시간과 최소 회의 시간을 반영한 후보 추천, 차선안 제시, 투표 및 최종 일정 확정 기능을 설계하였다. 유스케이스 다이어그램, ERD, 클래스 다이어그램을 통해 데이터 구조와 객체 간 관계를 정의하고, 데이터 무결성과 시간표 변경에 따른 재검사 방안을 마련하였다.

## 2. 현실적 제한조건

**관리적 제한**
- 팀원·기간: 5명이 한 학기(약 12주) 내 MVP 필수 기능 개발 완료.
- 개발 공정: 1~4주(설계·구조화), 5~7주(핵심 구현), 8~9주(통합·시각화), 10~12주(검증·시연)로 세분화.

**시스템적 제한**
- 인프라: 기존 '데이터베이스 미구축' 조건에서 선회하여 확장성·데이터 보존을 위해 **공식 데이터베이스 사용**.
- 입력 환경: 설치 없는 웹 기반. 에브리타임 캡처 **이미지 인식** + 개인 일정 **수기 입력** 병행. 미입력자가 '전원 참석 가능'으로 오연산되지 않도록 예외 처리.
- 데이터 규격: 모든 일정은 고정 단위 슬롯으로 분할 후 가능(1)/불가(0) 비트열로 규격화. 공통 시간 탐색 시 교집합 연산 + 이동 여유 시간 + 최소 회의 시간 알고리즘을 필수로 거침.
- 성능: 모임 인원 증가에도 핵심 연산·UI 응답 시간이 지연되지 않도록 최적화.

## 3. 설계 결정 진행 상황

### 가. ERD (Entity Relationship Diagram)

#### 1) 사용자·시간표 영역

**USER** — 소셜 로그인 사용자 정보와 시간표 등록 상태 관리
- 핵심 필드: `provider`·`provider_user_id`(소셜 계정 식별, 복합 유니크), `name`·`major`(프로필 필수), `profile_completed`(모임 참여 가능 여부), `timetable_registered_at`(NULL이면 미등록), `timetable_version`(수정 시 +1), `deleted_at`(탈퇴)
- 설계 포인트: 소셜 계정은 `(provider, provider_user_id)` 조합으로 식별하므로 서로 다른 플랫폼의 같은 ID도 충돌하지 않음.

**TimeTableSlot** — 주간 시간표를 요일·시간 단위로 저장 (한 행 = 수업 하나)
- 핵심 필드: `day_of_week`(0~6), `start_time`·`end_time`, `title`(과목명)
- 설계 포인트: 등록했지만 일정 0건인 사용자는 "공강이 많은 사람"으로 처리해 미등록자와 구분. 시작 시각 > 종료 시각 데이터는 CHECK 제약으로 차단.

#### 2) 모임·참여 영역

**Meeting** — 모임 기본정보, 공강 탐색 조건, 초대·공유 정보
- 핵심 필드: `name`·`description`, `period_start~end`(조회 기간), `search_start~end_time`(탐색 시간 범위), `travel_buffer_min`(이동 여유), `min_duration_min`(최소 회의시간), `needs_recalc`(재계산 필요), `invite_code`·`invite_expires_at`, `share_token`, `deleted_at`
- 설계 포인트: 구성원이 시간표 수정 시 같은 트랜잭션에서 `needs_recalc`만 true로 바뀌고 실제 재계산은 관리자가 실행. 일정 확정 여부는 별도 상태 컬럼 없이 `CONFIRMED_SCHEDULE` 존재 여부로 판단.

**MeetingMember** — 사용자와 모임을 연결, 역할 구분
- 핵심 필드: `role`(ADMIN/MEMBER), `status`(ACTIVE/LEFT)
- 설계 포인트: `(meeting_id, user_id)` 복합 유니크로 중복 가입 차단. 관리자도 구성원 테이블의 한 행이라 공통 기능 재사용. 관리자 위임은 두 사람의 role 변경을 한 트랜잭션으로 처리. 관리자가 1명뿐이면 위임/삭제 전 탈퇴 불가.

#### 3) 매칭·투표·확정 영역

**MatchingRun** — 공강 매칭 실행마다 쌓이는 계산 기록
- 핵심 필드: `trigger_type`(참여/관리자 재계산/확정 전 재검사), `cond_snapshot`(탐색 조건 JSON), `total_member_count`·`timetable_input_count`(시각화 인원), `input_hash`(시간표 상태), `calculated_at`
- 설계 포인트: 결과를 덮어쓰지 않고 이력으로 남겨 조건·구성원 변경 시에도 이전 결과와 섞이지 않음. 최신 결과는 `(meeting_id, calculated_at)` 인덱스로 조회.

**CandidateSet** — 한 번의 계산으로 만들어진 후보들을 투표 라운드 단위로 묶음
- 핵심 필드: `set_type`(일반 추천/차선책), `reason`(차선책 진입 사유), `result_status`(후보 있음/없음), `vote_status`(투표 중/마감/폐기)
- 설계 포인트: 재계산 시 기존 묶음은 "폐기"로 바뀌고 새 묶음 생성, 이전 투표는 기존 묶음에 보관.

**Candidate** — 추천 회의 시간 하나하나 (묶음당 최대 3개)
- 핵심 필드: `rank_no`(순위), `start_at`·`end_at`, `available_count`(참석 가능 인원)
- 설계 포인트: `(set_id, rank_no)` 복합 유니크. 불참 인원은 전체 인원 − 참석 가능 인원으로 계산.

**VoteBallot** — 구성원 1명이 후보 묶음 1개에 제출한 투표 1건
- 핵심 필드: `set_id`, `member_id`, `no_available`(선택 가능 후보 없음)
- 설계 포인트: `(set_id, member_id)` 복합 유니크로 1묶음 1구성원 1투표 제한.

**VoteSelection** — 투표지에서 선택한 후보 저장
- 핵심 필드: `ballot_id` + `candidate_id`(복합 PK), `set_id`(정합성 검증용)
- 설계 포인트: 투표지·후보를 `set_id`와 복합 FK로 참조해 다른 묶음 후보 선택을 DB에서 차단. "후보 없음" 투표지는 선택 항목이 없음.

**ConfirmedSchedule** — 관리자가 최종 확정한 모임 일정 (모임당 1개)
- 핵심 필드: `candidate_id`(확정 후보), `recheck_run_id`(확정 직전 재검사 기록), `confirmed_at`
- 설계 포인트: 확정 직전 최신 시간표 재검사 결과를 함께 남겨 신뢰성 보장. `meeting_id`는 "모임당 1개" 제약을 위해 함께 저장.

### 나. 클래스 다이어그램

#### 관계 표기

| 표기 | 의미 |
|---|---|
| 실선 | 두 클래스가 정보를 참조하는 연관 관계 |
| 검은 마름모 실선 (◆) | 전체 객체가 부분 객체를 소유하는 복합(composition) 관계 |
| 1 | 정확히 한 개 |
| 0..1 | 없거나 한 개 |
| 0..* | 없거나 여러 개 |

#### 클래스 관계

| # | 관계 | 다중성 | 설명 |
|:-:|---|:-:|---|
| ① | USER – MEETING_MEMBER | 1 – 0..* | 사용자 1명은 여러 모임 참여 정보를 가질 수 있고, 각 참여 정보는 정확히 한 명에게 속함 |
| ② | MEETING – MEETING_MEMBER | 1 – 0..* | 모임 1개는 여러 참여 정보를 가짐. USER–MEETING 다대다를 MEETING_MEMBER가 연결 |
| ③ | USER ◆– TIMETABLE_SLOT | 1 – 0..* | 사용자는 여러 시간표 항목을 **소유**(복합 관계). 미입력 사용자는 항목 없음 |
| ④ | USER – MEETING_MEMO | 1 – 0..* | 사용자 1명은 여러 메모 작성, 각 메모에 작성자 1명 |
| ⑤ | MEETING – MEETING_MEMO | 1 – 0..* | 모임 1개에 여러 메모, 각 메모는 모임 1개에 속함 |
| ⑥ | MEETING – MATCHING_RUN | 1 – 0..* | 모임은 공강 계산을 여러 번 실행, 각 이력은 모임 1개에 연결 |
| ⑦ | MEETING_MEMBER – VOTE_BALLOT | 1 – 0..* | 구성원은 여러 후보 집합에 투표 가능, 동일 집합에선 구성원당 1표 |
| ⑧ | MATCHING_RUN – CANDIDATE_SET | 1 – 0..* | 1회 계산은 추천·차선 후보 집합 생성, 각 집합은 계산 1건에서 생성 |
| ⑨ | CANDIDATE_SET – VOTE_BALLOT | 1 – 0..* | 후보 집합 1개에 여러 투표 응답 연결 |
| ⑩ | CANDIDATE_SET ◆– CANDIDATE | 1 – 0..* | 후보 집합은 개별 후보를 **소유**(복합). 최대 3개 제한은 업무 규칙 |
| ⑪ | VOTE_BALLOT ◆– VOTE_SELECTION | 1 – 0..* | 투표 응답은 선택 항목을 **소유**(복합). "후보 없음"이면 0개 |
| ⑫ | CANDIDATE – VOTE_SELECTION | 1 – 0..* | 후보 1개는 여러 구성원에게 선택됨 → 득표수 집계 |
| ⑬ | CANDIDATE – CONFIRMED_SCHEDULE | 1 – 0..* | 확정 일정은 후보 1개 참조 (업무 규칙 엄격 적용 시 0..1로 축소 가능) |
| ⑭ | MEETING – CONFIRMED_SCHEDULE | 1 – 0..1 | 모임은 최대 1개의 확정 일정 |
| ⑮ | MATCHING_RUN – CONFIRMED_SCHEDULE | 1 – 0..* | 확정 일정은 확정 전 수행한 재검사 이력 1건 참조 |

#### 클래스별 속성·기능 (Java 자료형 기준)

**User** — 소셜 계정·프로필·시간표 등록 상태 관리
- 속성: `user_id`(Long), `provider`(String), `provider_user_id`(String), `name`(String), `major`(String), `profile_completed`(Boolean), `timetable_registered_at`(LocalDateTime), `timetable_version`(Integer), `deleted_at`(LocalDateTime)
- 기능: `socialLogin():USER`, `updateProfile():void`, `importTimetable():void`(OCR/AI 분석), `saveTimetable():void`, `updateTimetable():void`(버전 갱신 + 재계산 필요 표시), `logout():void`

**TimeTable_Slot** — 개별 수업/일정 (공강 계산 시 불참 구간 판단 자료)
- 속성: `slot_id`(Long), `user_id`(Long), `day_of_week`(Integer), `start_time`(LocalTime), `end_time`(LocalTime), `title`(String)
- 기능: `validateTime():Boolean`, `update():void`, `overlaps():Boolean`

**Meeting** — 모임 기본 정보·공강 검색 조건
- 속성: `meeting_id`(Long), `name`(String), `description`(String), `period_start`·`period_end`(LocalDate), `search_start_time`·`search_end_time`(LocalTime), `travel_buffer_min`(Integer), `min_duration_min`(Integer), `needs_recalc`(Boolean), `invite_code`(String), `invite_expires_at`(LocalDateTime), `share_token`(String), `deleted_at`(LocalDateTime)
- 기능: `create():MEETING`, `updateConditions():void`, `createInvite():String`, `onMemberJoined():MATCHING_RUN`, `recalculate():MATCHING_RUN`, `confirm():CONFIRMED_SCHEDULE`, `delete():void`

**Meeting_Member** — 사용자-모임 참여 관계, 역할·상태
- 속성: `member_id`(Long), `meeting_id`(Long), `user_id`(Long), `role`(String: ADMIN/MEMBER), `status`(String: ACTIVE/LEFT)
- 기능: `acceptInvite():void`, `isAdmin():Boolean`, `transferAdmin():void`, `leave():void`

**Meeting_Memo** — 모임 안내·의견 기록
- 속성: `memo_id`(Long), `meeting_id`(Long), `author_user_id`(Long), `content`(String), `deleted_at`(LocalDateTime)
- 기능: `write():void`, `update():void`, `delete():void`

**Matching_Run** — 공강 계산 실행·이력
- 속성: `run_id`(Long), `meeting_id`(Long), `trigger_type`(String), `cond_snapshot`(Map<String,Object>), `total_member_count`(Integer), `timetable_input_count`(Integer), `input_hash`(String), `calculated_at`(LocalDateTime)
- 기능: `calculate():CANDIDATE_SET`, `findCommonFreeTime():CANDIDATE[]`, `recommendTop3():CANDIDATE_SET`, `recheck():Boolean`

**Candidate_Set** — 후보 묶음, 투표 진행·집계
- 속성: `set_id`(Long), `run_id`(Long), `set_type`(String), `reason`(String), `result_status`(String), `vote_status`(String)
- 기능: `openVote():void`, `countVotes():Integer[]`, `closeVote():void`, `getWinner():CANDIDATE`

**Candidate** — 개별 시간대 후보
- 속성: `candidate_id`(Long), `set_id`(Long), `rank_no`(Integer), `start_at`(LocalDateTime), `end_at`(LocalDateTime), `available_count`(Integer)
- 기능: `isAvailable():Boolean`, `getVoteCount():Integer`

**Vote_Ballot** — 구성원 1명의 투표 응답
- 속성: `ballot_id`(Long), `set_id`(Long), `member_id`(Long), `no_available`(Boolean)
- 기능: `submit():void`, `update():void`, `markNoAvailable():void`

**Vote_Selection** — 투표 응답에서 선택한 후보
- 속성: `ballot_id`(Long), `set_id`(Long), `candidate_id`(Long)
- 기능: `select():void`, `cancel():void`

**Confirmed_Schedule** — 확정 일정
- 속성: `confirmed_id`(Long), `meeting_id`(Long), `candidate_id`(Long), `recheck_run_id`(Long), `confirmed_at`(LocalDateTime)
- 기능: `confirm():void`, `getSchedule():CANDIDATE`, `getShareLink():String`

> **설계 참고:** 현재 모델에는 초대 대상·미수락 상태를 기록하는 구조가 없어 '초대받은 팀원 전원 수락 여부' 판정을 위해서는 보완 필요. 메서드 매개변수 생략은 다이어그램 간결화를 위한 것.

### 다. 문제해결에 적용된 이론 — 비트 벡터 공강 계산

- 주간 시간표를 **120개 시간 슬롯**으로 구분, 각 슬롯을 가능(1)/불가(0) **비트 벡터**로 모델링. 64비트 워드 기준 약 2~3개 워드에 표현.
- 공통 참석 가능 시간은 각 참여자 비트 벡터에 **비트 AND 연산**을 반복 적용. 모든 참여자가 1인 위치만 결과 1.
- 워드 단위 연산으로 최대 64슬롯을 한 번에 처리. 워드 연산 횟수 = `O(N × ⌈S/w⌉)`. 본 시스템은 S=120 고정이므로 참여자 수 N에 대해 **선형 O(N)**.

### 라. SW 설계 방법론 — 애자일 MVP

폭포수 대신 애자일 채택. (1) 개인과 상호작용 — 소통·협업 우선, (2) 우선순위 반복 개발 — 비트 연산 매칭·컬러맵이 실제 구동되는 MVP 집중, (3) 빠른 피드백 — 초기 배포로 수기 입력·뷰어 직관성 피드백 반영, (4) 변화 대응 — DB 미구축 → DB 도입 등 궤도 수정 수용.

## 4. 설계 평가

| 평가 영역 | 검증 방법 |
|---|---|
| 핵심 알고리즘 성능·정확도 | 인원(N)을 극단적으로 늘려 O(N) 유지 및 수초 이내 응답 확인. 이동 여유·최소 회의 조건 반영 결과가 기준 알고리즘과 일치하는지 검증 |
| 예외 상황·차선책 도출 | 공통 공강 0 상황에서 멈춤 없이 최대 다수 참석 차선책 제안 확인. 미입력자가 전원 참석으로 연산되지 않는지 확인 |
| 데이터 무결성·변환 | 주간 시간표가 120비트 벡터로 정확히 변환·저장·조회되는지 테스트 |
| 활용성 | 누적 인원 비례 컬러맵 정확 표시 확인. 로그인~확정 통합 테스트로 끊김 없는지 확인 |
